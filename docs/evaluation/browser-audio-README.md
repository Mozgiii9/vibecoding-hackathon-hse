# Реальный браузерный проход аудио

`browser-audio.mjs` работает с настоящим UI и backend. Он не запускает сервисы, не подменяет ответы и не использует `page.route`. Сначала подготовьте отдельную пустую runtime memory, auth в режиме `local`, реальный Gemini и STT. По умолчанию UI доступен на `http://127.0.0.1:16073`; его `/api` должен проксировать настоящий gateway (для изолированной проверки B — порт `18788`). Нельзя направлять этот тест на личную учётную запись или общую память: он создаёт владельца и цель `demo`, импортирует синтетическую запись и подтверждает одно действие.

Зависимости берутся из установленного `app/builds/typescript/client_web/node_modules/@playwright/test`. Chromium должен быть установлен отдельно. Runner не устанавливает браузеры и зависимости.

При несовпадении bundled revision укажите уже установленный браузер через `AUDIO_SMOKE_EXECUTABLE`. На машине B установлен Chromium1243, тогда как текущая зависимость ожидает1228. Для audio payload runner пассивно читает clone настоящего fetch response внутри страницы: CDP `response.json()` на этом сочетании версий ошибался после фактического успешного ответа сервера. Никакой ответ не заменяется, original fetch/response возвращается приложению неизменным; auth responses и headers не наблюдаются.

Из корня репозитория, после готовности сервисов:

```powershell
node docs/evaluation/browser-audio.mjs
```

При стандартном запуске имя и сильный пароль синтетического владельца создаются в памяти процесса. Пароль не печатается и не сохраняется. Повторный запуск требует новой изолированной auth/memory: runner намеренно ничего не удаляет. Для известного синтетического владельца задайте `AUDIO_SMOKE_USERNAME` и `AUDIO_SMOKE_PASSWORD` приватно через окружение. `AUDIO_SMOKE_LOGIN_ONLY=1` пропускает только создание аккаунта, используя обычный UI-вход; цель `demo` при этом всё равно должна отсутствовать. Это отдельный режим, не доказательство чистой регистрации. Не задавайте секреты в опубликованных командах или документах.

Параметры окружения:

| Переменная | Назначение |
|---|---|
| `AUDIO_SMOKE_BASE_URL` | URL отдельного UI на loopback; по умолчанию `http://127.0.0.1:16073` |
| `AUDIO_SMOKE_OUTPUT` | Каталог результатов; по умолчанию `docs/evaluation/browser-audio-artifacts` |
| `AUDIO_SMOKE_TIMEOUT_MS` | Ожидание настоящего STT/LLM, по умолчанию 240 000 мс |
| `AUDIO_SMOKE_EXECUTABLE` | Абсолютный путь к установленному Chromium при необходимости |
| `AUDIO_SMOKE_CHANNEL` | Канал Playwright, например `chrome`, при необходимости |
| `AUDIO_SMOKE_HEADED=1` | Открыть видимый браузер |
| `AUDIO_SMOKE_USERNAME`, `AUDIO_SMOKE_PASSWORD` | Только синтетические тестовые credentials; без сохранения в отчёте |
| `AUDIO_SMOKE_LOGIN_ONLY=1` | Обычный вход существующего синтетического аккаунта; без clean-signup приёмки |

Runner последовательно проверяет:

1. `GET /api/auth/bootstrap-status`: режим `local`, аккаунт отсутствует; UI `Username`, `#new-password`, `#confirm-password`, `Create account`; затем `Выйти` и обычный `Sign in` через `#identifier` / `#password`.
2. `Заполнить пример про ML-стажировку` → `Подтвердить цель и критерии`; сервер подтвердил цель `demo`, три счётчика равны нулю.
3. `Добавить контекст` → `Аудио`, `Название источника`, `Аудиофайл` → настоящий `docs/demo/sources/demo-audio.wav` → `Найти события`. Принимается только реальный успешный ответ `/api/context/audio` с непустой расшифровкой, evidence и правильным hash `SHA-256("audio" + NUL + raw bytes)`. Все цитаты равны точному срезу расшифровки; импорт без подтверждения не увеличивает прогресс.
4. Карточка настоящего `completed_action` → `Посмотреть источник`; выделенный `<mark>` равен его точной цитате → явный клик `Подтвердить`. Проверяются настоящий PATCH, серверный счётчик, evidence ID в прогрессе и UI progressbar.
5. Те же исходные bytes через UI с другим названием: `duplicate: true`, прежние source/hash/evidence IDs, неизменные число evidence и серверный прогресс. Отдельного прямого доказательства числа вызовов STT из браузера нет: результат содержит `NOT_OBSERVABLE_FROM_BROWSER`. Для доказательства пропуска STT сопоставьте этот проход с отдельной сервисной телеметрией; время ответа само по себе этого не доказывает.
6. Reload сохраняет авторизацию, цель, события и подтверждённый прогресс. Это проверка браузерного reload, а не restart процесса.

Проверочные GET идут из браузера с настоящими credentials/cookie: `/api/auth/refresh` выдаёт bearer внутри страницы, затем fetch читает progress/evidence. Token не покидает страницу, не сохраняется и не выводится. Все записи состояния выполняются UI. Auth-ответы, сетевые заголовки, cookies, пароль, trace и console dump не сохраняются.

`results.json` содержит PASS/FAIL, фактический Git SHA, признак незакоммиченных tracked-изменений, SHA-256 самого runner и аудиофайла, синтетическую расшифровку/evidence, счётчики и имена скриншотов. Скриншоты создаются после входа, включая раскрытый источник с точной цитатой. Ошибка хранит безопасный stage/type без сырого Playwright exception, который мог бы включить введённое значение. Exit code — 0 при PASS и 1 при FAIL.

Наличие runner не означает, что он уже запущен или что полный MVP принят. Результаты относятся к указанному SHA и его текущим локальным изменениям. Restart/backup, отрицательные сценарии, мобильная проверка и независимое число provider-вызовов остаются отдельной приёмкой. Не коммитьте результаты чужих/личных данных; этот проход разрешён только на синтетическом окружении.

Canonical runner поддерживает как русский текущий UI (`Создать аккаунт`, `Войти`), так и английский первый экран первой волны. Он побайтно совпадает с прошедшим common-candidate runner из отчёта ef360ae.
