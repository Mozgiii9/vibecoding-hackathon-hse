# Приёмка extraction и проверка цитат

`acceptance-corpus.json` содержит 10 синтетических случаев: 9 запросов настоящей модели и одну отдельную parser/validation проверку неоднозначной цитаты. `parser-cases.json` добавляет семь детерминированных проверок границ. Это небольшой приёмочный набор, а не общая метрика качества модели.

Перед запуском собрать текущий backend: из `app/builds/typescript` выполнить `npm run build`. Runner динамически импортирует реальные `createContextProviders`, `readHackathonProviderConfig`, `parseExtractionResponse`, `validateEvidence` из `dist`; собственной реализации extraction и подставного сетевого ответа в нём нет.

Из корня репозитория:

```sh
# Без ключей и сети: 8 parser/validation случаев, включая неоднозначную цитату.
node docs/evaluation/run-context-evaluation.mjs --parser-only

# Настоящие модельные вызовы с server-side environment текущего процесса.
node docs/evaluation/run-context-evaluation.mjs

# Ограниченный повтор отдельных случаев; не заменяет весь прогон.
node docs/evaluation/run-context-evaluation.mjs --cases=negation,instructions-in-source --output=docs/evaluation/live-negative-results.json
```

Live-режиму нужны уже разрешённые `HACKATHON_LLM_PROTOCOL`, `HACKATHON_LLM_BASE_URL`, `HACKATHON_LLM_MODEL`, `HACKATHON_LLM_API_KEY`, опционально `HACKATHON_LLM_TIMEOUT_MS`. Не передавать ключ аргументом команды, не печатать environment и не сохранять его в tracked файлах. Для безопасной передачи из уже работающего процесса runner экспортирует `runEvaluation({ env, parserOnly, outputPath, caseIds })`; объект `env` передаётся только в памяти. Никакого автоматического fallback нет.

Выход по умолчанию — `parser-results.json` или `live-results.json`. В отчёте: SHA исходной ветки, hash фактически импортированных built modules и корпуса, expected/actual, точные цитаты, проверка offsets, latency каждого запроса и фиксированные безопасные коды ошибок. URL, ключи, сырые provider responses и модельные summaries не записываются. Перед передачей отчёта всё равно проверить diff; использовать только синтетические входы.

`semanticMatch` сравнивает весь набор пар criterion/eventType, `quoteMatch` — строгие тройки criterion/eventType/эталонная цитата. `quoteValid` отдельно проверяет точное совпадение фактической цитаты с диапазоном в исходном тексте. Другая корректная граница цитаты может дать `quoteValid=true`, `semanticMatch=true`, `quoteMatch=false`; runner честно помечает строгий кейс FAIL, а человек разбирает отличие. На rejected-ответе `quoteValid=null`, а не фиктивный PASS.

У неоднозначной цитаты тест передаёт заранее объявленный JSON в **настоящий парсер и валидатор**, а не в модель. JSON должен распарситься; повторяющаяся цитата без обоих offsets должна дать `provider_failed`. В отдельном положительном случае явные корректные offsets повторяющейся цитаты принимаются. Семантическую истинность события валидатор не устанавливает: нельзя путать точную цитату с доказательством факта.

Коды завершения: 0 — все выбранные случаи прошли; 1 — есть FAIL; 2 — runner не смог запуститься (сборка или environment). Нет ключа — live NOT_RUN, parser-only это не меняет. Этот runner не проверяет STT, UI, atomic commit, сохранность и прогресс; эти пункты требуют отдельного сквозного прохода.

## AI pipeline для защиты

Пользователь сначала подтверждает цель и измеримые критерии. Текст попадает в extraction без изменения; для аудио сначала нужен настоящий STT, который возвращает расшифровку и доступные временные сегменты. Модель сопоставляет описанное событие с критерием, различает действие, намерение, препятствие и неопределённость и предлагает точную цитату. Встроенные инструкции источника считаются данными.

Код проверяет допустимый criterionId, схему ответа и совпадение цитаты с исходным текстом по UTF-16 offsets. Если offsets отсутствуют, цитата должна встречаться ровно один раз; времена берутся только из STT. Лишь после проверки core атомарно сохраняет источник и предложенные события, с защитой от повторного импорта. Модель не подтверждает прогресс: пользователь проверяет основание и принимает или отклоняет карточку. Счётчик считает только подтверждённые `completed_action`, а следующий шаг в текущем MVP выбирается правилом по незакрытому критерию.

Самоотчёт остаётся самоотчётом: точная цитата обеспечивает прослеживаемость, а не независимую проверку реального мира. Примеры демонстрации и ожидаемые счётчики находятся в `docs/demo/sources/EXPECTED.md`.
