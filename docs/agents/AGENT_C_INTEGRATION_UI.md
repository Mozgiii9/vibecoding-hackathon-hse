# Текущий Codex — интеграция и интерфейс

Ветка **`codex/integration-ui`**. Пользователь ведёт визуальный дизайн в Google Stitch; Codex превращает выбранный дизайн в работающий React интерфейс и объединяет backend модулей A/B. Эта роль сохраняет единоличное владение общими точками.

## Владение

- `app/builds/typescript/features/contracts.ts`, `docs/contracts/**`, общий fixture.
- `app/builds/typescript/gateway/server.ts` и необходимая конфигурация providers/запуска.
- `app/builds/typescript/client_web/**`, включая app shell, API adapter, UI states и стили.
- Корневые docs/README, согласованные изменения manifests/lockfiles, сценарий интеграционной проверки.
- Не переписывать A/B модули параллельно с их владельцами. При блокирующем дефекте передать пример и исправление владельцу или договориться о временной передаче файла.

## До первой интеграции

1. Общий bootstrap уже содержит исходники BrainDrive, API и типы. Проверить, что обе remote ветки стартовали от этого коммита.
2. Получить от владельца base URL, точный model ID и протокол кастомного Gemini провайдера безопасным локальным способом. Подготовить environment-конфигурацию без ключей в git. Отдельно узнать поддержку STT.
3. Сделать типизированный frontend adapter под API_V1. Использовать существующий auth adapter и `/api`; fixture только для UI разработки, с явным режимом. Не дублировать ручной bearer token в каждом компоненте.
4. Экран цели: ввод/подтверждение трёх критериев, импорт текста/файла, события, подтверждение/отклонение, раскрытие источника, прогресс. До Stitch использовать рабочий минимальный layout; утверждённый дизайн подключать без изменения доменной логики.
5. Создать UI состояния: пустая цель, обработка, ошибка провайдера, нет STT, повторный источник, конфликт revision, неизвестность, все критерии выполнены. После PATCH получать свежий progress, не вычислять его независимо в браузере.

## Интеграция

В gateway создать один GoalsStore с runtime memoryRoot, создать ContextProviders из server environment, зарегистрировать оба route module после существующих auth hooks. Не трогать старый endpoint uploads с HTTP 410. Проверить, что новые routes реально защищены через app.inject и HTTP, а не только «расположены ниже» middleware в тексте файла.

После появления первых компилируемых коммитов A/B сделать обычный merge их веток в свою. Не менять их историю. При необходимости дождаться exports, работать с UI fixture, не создавать конкурирующую реализацию core/context.

Первый сквозной сценарий к 14:15: login → goal confirm → text import → source quote → evidence confirm → progress → duplicate import → reject → restart. До 15:15 подключить аудио, если оно действительно работает.

## Stitch

Проверка list_projects успешна 25 октября около 12:55 МСК. Это подтверждает доступ на чтение, не успех генерации или экспорта. Новый дизайн пока не создан. Использовать отдельный проект хакатона, не редактировать существующие сторонние проекты. Пользователь выбирает визуальный вариант.

Полученный HTML — ориентир/материал для переноса в текущий React, не второй самостоятельный SPA. Через доступный Stitch download_file получать HTML, не скачивать credential URLs напрямую. Не подключать внешний Tailwind CDN в приложение. Текст и состояния — по контракту продукта. Сохранять рабочую авторизацию и лицензии основы. Бюджет на первый выбранный экран — около 20 минут; если генерация задерживается, продолжать рабочий UI без неё.

## Проверки и сдача

- Сборки backend/MCP/frontend, тесты A/B, frontend сценарий подтверждения/ошибки/дубля.
- Реальный вызов настроенного Gemini на синтетическом контексте, отдельно реальные STT capabilities.
- Проверка UI в браузере без захвата фокуса: desktop и узкий экран, keyboard/focus, нет скрытых неработающих действий.
- HTTP auth, отсутствие ключей в JS bundle/логах, хранение внутри runtime memory, сохранность после restart.
- Пробный запуск на машине показа; сервер — только после проверки ресурсов. Если сервер мешает, ноутбук остаётся резервом.
- В 15:45 feature freeze; к 16:45 записать реальное demo, 4 слайда; к 17:15 полный комплект.

Сабагенты допустимы: frontend reviewer в read-only режиме; integration test helper с одним явно закреплённым тестовым файлом. Не отправлять внешним агентам сообщения без явного разрешения пользователя; обмен через Git и передаваемые людьми статусы.
