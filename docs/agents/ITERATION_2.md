## Ветки и владение после команды на старт

Ветки A/B второй волны создаются от **актуального `origin/codex/integration-ui` с этим планированием**, имеющего `35b093b` в истории. `main` пока не содержит интегрированного MVP. Старые ветки и их историю не переписывать. Перед началом записать фактический базовый SHA в свой status.

| Кто | Планируемая ветка | Файлы |

| A | `codex/qa-release` | `app/builds/typescript/features/goals/**`, `app/builds/typescript/client_web/e2e/release-*.spec.ts`, `scripts/release/**`, `app/installer/hackathon/**`, `docs/release/**`, свой status/handoff |

Общий Playwright config принадлежит C. A при необходимости использует отдельный release runner/config в своих путях. Новые `scripts/release`, `services/stt` и packaging-пути — предложения, пока их нет. Изменение чужого файла сначала передаётся владельцу с воспроизведением либо явно согласуется как передача файла.

```bash

# Проверить сохранность текущих изменений перед переключением.
git status --short
```

Для B имя `codex/audio-quality`. Если ветка существует — проверить историю и использовать её, без force/reset/автоматического stash.

## Очереди без ожидания

| Агент | Основная очередь | При блокировке |
|---|---|---|
| A | A1 браузерная приёмка → A2 source-build/чистый запуск → A3 restart/backup/runbook → A4 независимая проверка кандидата | Нет ключа: A2/A3 и auth/создание цели. Нет Docker/VPS: доступная локальная сборка и инструкция, серверную часть пометить NOT_RUN |
| B | B1 проверка доступного STT за 10 минут → B2 один реальный adapter → B3 качество → B4 demo-корпус | Нет рабочего STT: сразу B3/B4, вернуться при конкретном ресурсе. Нет ключа: parser/negative cases и корпус; не называть это live quality |
| C | C1 живой текст → C2 первый вход/дизайн/ошибки → C3 частая интеграция → C4 пакет защиты | Нет ключа: UI и материалы; нет B: текстовый путь; нет упаковки A: ноутбук как машина показа |

После готовой задачи агент сам берёт следующую доступную из своей очереди, не спрашивает «что дальше». Зависимость не разрешается 5 минут — фиксирует blocker и переключается. Первый небольшой проверенный результат публикует за 20–30 минут, не в конце всей очереди.

Каждый пишет только свой `docs/status/agent-a.md`, `agent-b.md` или `agent-c.md` на границах задач, ориентир раз в 15–20 минут активной работы. Статус содержит: ID задачи, состояние, base SHA, ready SHA, проверки, blocker и следующую доступную задачу. Ключи/токены туда не попадают. C рассматривает опубликованные части каждые 20–30 минут активной работы и делает обычный merge, не ожидая завершения обеих веток. Это порядок работы, не фоновая автоматизация.

Состояния: `PLANNED`, `RUNNING`, `BLOCKED`, `READY_FOR_INTEGRATION`, `INTEGRATED`, `ACCEPTED`. Тесты одной ветки не означают приёмку всего продукта. Не устраивать бесконечный polling; когда вся доступная очередь завершена, сделать handoff и остановиться до нового поручения, не придумывая лишние функции.

Сабагенты: GPT‑6.1‑Sol/high, до двух одновременно у каждого родителя, непересекающиеся файлы/worktrees. Родитель отвечает за интеграцию и коммит. Использовать реализацию + независимую проверку либо два независимых компонента, не дублировать весь продукт.

## Готовность

Обычный вход и живой UI, намерение не засчитано, действие подтверждено с цитатой, дубль не увеличивает счётчик, reject/restart сохраняют результат. Запускается зафиксированный **наш код**, память постоянна, ключи серверные. Аудио либо реально проверено, либо не обещается. Есть трёхминутный показ и резервная запись с ясным собственным вкладом поверх MIT-основы.

Подготовка пакета не запускает deployment: реальные серверные операции — после отдельного указания владельца на целевое окружение. Если сервер не готов к 15:00, основной машиной показа остаётся проверенный ноутбук.
