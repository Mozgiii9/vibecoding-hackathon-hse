Один человек/агент владеет одним изменяемым файлом. A и B не правят gateway, shared contract, package.json/lockfiles или frontend. Новую зависимость сначала обосновать интегратору; по умолчанию достаточно встроенных Node API, Fastify и Zod. Другие AGENTS.md внутри `app/` прочитать перед работой. Пользователь разрешил сабагентов для ускорения разработки и ревью.

Упоминания `dev`, `model/glm-5.2` и других веток в upstream AGENTS.md относятся к исходному BrainDrive. Для этого форка пользовательским заданием назначены только ветки из таблицы, от общего bootstrap в main. Не переключаться на upstream ветки и не искать его закрытые проекты.

## Начало работы

1. Получить актуальный `main`; он должен содержать `app/`, `features/contracts.ts` и эти задания. Все три удалённые ветки создаются от одного стартового коммита. Проверить это до начала реализации.
2. На своей машине выбрать только свою remote tracking ветку. Не переключать ветку в общем checkout, пока другой агент пишет файлы. Для сабагентов использовать отдельные worktrees или строго непересекающиеся файлы.
3. Прочитать свой файл, API_V1.md и contracts.ts. Реализация в задании разрешена после того, как владелец отправил агенту стартовый промпт; не нужно повторно согласовывать обычные шаги внутри этой границы. Непредусмотренные изменения контракта обсуждать.
4. До ключей провайдера и соседней реализации работать с фейком порта в тестах. Фейк не подключать в обычном запуске без явного demo-режима.

Пример для A в уже клонированном репозитории:

```bash
# Обновить сведения о ветках, не меняя рабочие файлы.
git fetch origin
# Создать локальную ветку из общей стартовой remote ветки, если локальной ещё нет.
git switch --track origin/codex/goals-core
```

Если ветка уже существует локально, использовать `git switch codex/goals-core`, предварительно проверив `git status`. Для B заменить имя на `codex/context-ingest`.

## Общие решения

- Основной LLM — пользовательский провайдер с Gemini. Название модели, URL и протокол ещё не подтверждены. OpenRouter — резерв, не автоматический fallback. Ключи в чат, git и frontend не помещать.
- Поддержка аудио у основного провайдера неизвестна. B отдельно проверяет STT; если его нет, текстовый сценарий остаётся рабочим, аудио честно возвращает `stt_unconfigured`.
- A — единственный писатель состояния целей, источников и evidence. B вызывает `ContextStore`, собственного хранилища не делает. Схема данных не зависит от того, какая модель выбрана.
- Общий синтетический fixture: `docs/contracts/demo-fixture.json`. Он не подключается в рабочий режим как якобы реальный результат модели.
- Один процесс gateway и один владелец данных для MVP. Новые маршруты защищаются существующей авторизацией BrainDrive. Не превращать локальный режим в обход авторизации.
- Сначала текстовый сквозной сценарий. Дизайн Stitch и аудио не блокируют API и тесты.

## Коммиты и интеграция

- Каждый коммитит и push только свою ветку, без force push и без самостоятельного merge в main. Использовать существующие pre-commit hooks, не обходить их; если hooks не настроены, выполнить минимум `git diff --cached --check` и проверки своего модуля.
- Не ждать конца работы: первый компилируемый модуль отправить сразу. В handoff записать SHA, экспорты, команды и результаты тестов, незакрытые вопросы. Сообщение владельцу команды содержит ссылку на ветку и handoff.
- Наш Codex получает A и B через обычный merge в `codex/integration-ui`, разрешает конфликты общих точек, запускает проверки и затем fast-forward/обычный merge в main. Встречные merge UI-ветки в ветки A/B не делать без договорённости.
- Контракт после старта меняет только интегратор и уведомляет владельцев обеих веток. План не предполагает, что агенты на разных компьютерах могут напрямую переписываться: передача через ветки и людей.
- При разрешённом создании PR использовать один PR на ветку и описывать фактическую реализацию; PR не обязателен для первой передачи. Никакие задачи/сообщения другим чатам автоматически не отправлены.

## Сабагенты

Рекомендуется не больше двух одновременно на агента: один помогает с отдельным компонентом, второй проверяет крайние случаи и тесты. Родитель отвечает за интеграцию и итоговый коммит. Сабагент не меняет общий контракт, не коммитит в чужую ветку и не запускает внешние сообщения. Дублировать весь продукт между сабагентами запрещено: это увеличит конфликты вместо ускорения.
